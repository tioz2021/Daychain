## 1. Общие сведения

### 1.1. Цель

Локальное однопользовательское приложение для отслеживания личных привычек: список привычек с гибким расписанием, ежедневные отметки, серии (streaks), календарь активности и статистика. Проект делается для собственного использования, с расчётом на публикацию в открытом репозитории и запуск другими людьми без установки зависимостей.

### 1.2. Ключевые решения

| Решение | Значение |
|---|---|
| Язык ядра | C11, без внешних библиотек (только libc и POSIX) |
| Интерфейс | Web UI: HTML + CSS + ES-модули, без сборщика и без npm |
| Доставка UI | ассеты вшиваются в бинарник, опционально отдаются с диска (`--web-dir`) |
| Архитектура | один процесс: HTTP-сервер + ядро + хранилище в одном бинарнике |
| Хранение | JSONL-файл, снапшот состояния, атомарная перезапись |
| Расположение данных | папка `data/` рядом с бинарником (портативно) |
| Пользователи | ровно один, без авторизации |
| Сеть | только `127.0.0.1`, без TLS |
| Платформа | Linux (x86_64, aarch64), gcc/clang |
| Языки интерфейса | en, ru, uk |
| Начало суток | 00:00 локального времени системы |

### 1.3. Что входит и что не входит

**Входит в v1.0:** CRUD привычек, три вида расписания, бинарные отметки «выполнено / пропущено», заметка к отметке, календарь-heatmap, текущая и лучшая серия, процент выполнения, архив привычек, три языка, светлая/тёмная тема, экспорт JSONL, атомарное хранение и восстановление после сбоя.

**Добавлено в v1.1:** раздел «Вредные привычки» (quitting) — счётчик времени воздержания с живым таймером (дни, часы, минуты, секунды), лучший результат, число попыток и сброс «сорвался» с сохранением результата в статистике.

**Не входит (см. раздел 14):** напоминания и уведомления, счётчики и частичное выполнение, многопользовательский режим, синхронизация, мобильное приложение, PWA/service worker, авторизация, TLS, импорт данных, теги, подзадачи, графики кроме heatmap.

### 1.4. Глоссарий

| Термин | Значение |
|---|---|
| Привычка (habit) | Отслеживаемая активность с расписанием |
| Расписание (schedule) | Правило, определяющее, в какие дни привычку следует выполнять |
| Плановый день | Дата, в которую по расписанию привычку надо выполнить |
| Отметка (entry) | Запись «эта привычка в этот день выполнена/пропущена» |
| Серия (streak) | Количество подряд идущих плановых периодов без нарушения |
| Пропуск (skipped) | Осознанная отметка «не выполнял по уважительной причине» |
| Промах (miss) | Плановый день, прошедший без отметки |
| Снапшот | Файл, содержащий полное состояние данных, а не журнал изменений |

## 2. Пользователь и сценарии

### 2.1. Профиль

Один человек, работает за тем же компьютером, где запущено приложение. Запускает бинарник из терминала или ярлыка, браузер открывается автоматически. Приложение живёт, пока открыт процесс: закрыл терминал — данные уже сохранены на диск, повторный запуск поднимает состояние.

### 2.2. Сценарии использования

| ID | Сценарий |
|---|---|
| US-1 | Запустить приложение и увидеть список привычек на сегодня с отметками |
| US-2 | Создать привычку: название, цвет, иконка, категория, расписание |
| US-3 | Отметить привычку выполненной на сегодня одним нажатием |
| US-4 | Отметить прошедший день (вчера, позавчера) или исправить ошибочную отметку |
| US-5 | Поставить пропуск с пояснением, чтобы серия не порвалась |
| US-6 | Открыть статистику привычки: серия, лучшая серия, процент, heatmap за 12 недель |
| US-7 | Отредактировать привычку, сменить расписание, заархивировать |
| US-8 | Переключить язык интерфейса и тему |
| US-9 | Скачать копию данных одним файлом (экспорт) |
| US-10 | Перенести папку приложения на другой компьютер вместе с данными |

### 2.3. Ограничения пользовательского опыта

- Основное действие (отметка «выполнено») — не более одного клика или нажатия `Space` на выделенной привычке.
- Переход между днями — стрелками `←`/`→`, без перезагрузки страницы.
- Интерфейс пригоден на экране от 360 px по ширине.
- Никаких модальных окон при обычной отметке; модалки — только для создания/редактирования и подтверждения удаления.

## 4. Модель данных

### 4.1. Файл хранилища

`data/habits.jsonl` — UTF-8 без BOM, по одному JSON-объекту на строку, разделитель `\n` (в конце последней строки тоже). Файл является **снапшотом состояния**: при любом изменении перезаписывается целиком.

Первая строка — метаданные:

```json
{"type":"meta","schema_version":2,"app":"habits","created_at":"2026-10-30T19:45:00+02:00"}
```

Далее строки типов `habit`, `entry` и `quit` (v1.1) в произвольном порядке. `schema_version = 2`; файлы версии 1 читаются без миграции. Строки с неизвестным `type` игнорируются логикой, но сохраняются при перезаписи (прямая совместимость вперёд).

Почему снапшот, а не журнал событий: при объёме в десятки-сотни килобайт полная перезапись атомарна и исключает целый класс ошибок реплея и компакции; файл остаётся читаемым и пригодным для `git diff` и ручной правки. Переход на журнал событий (для истории и undo) возможен позже — для этого и существует `schema_version`.

### 4.2. Habit

```json
{"type":"habit","id":1,"name":"Чтение","description":"30 минут перед сном",
 "color":"#4f8cff","icon":"book","category":"развитие",
 "schedule":{"kind":"weekdays","days":[1,2,3,4,5]},
 "start_date":"2026-10-30","created_at":"2026-10-30T19:50:12+02:00",
 "archived_at":null,"sort_order":10,"value":null}
```

| Поле | Тип | Обяз. | Правила |
|---|---|---|---|
| `type` | string | да | всегда `"habit"` |
| `id` | integer | да | ≥ 1, уникален, выдаётся сервером как `max(id)+1` |
| `name` | string | да | после trim 1..80 символов Unicode (считаем код-поинты, не байты) |
| `description` | string | нет | 0..2000 символов, по умолчанию `""` |
| `color` | string | нет | `#rrggbb`, нижний регистр, по умолчанию `"#4f8cff"` |
| `icon` | string | нет | ключ из встроенного набора, иначе `"dot"` |
| `category` | string \| null | нет | 0..40 символов, свободный текст, по умолчанию `null` |
| `schedule` | object | да | см. 4.4 |
| `start_date` | string(date) | да | `YYYY-MM-DD`; раньше этой даты привычка не существует |
| `created_at` | string(datetime) | да | ISO 8601 с offset, ставит сервер |
| `archived_at` | string(date) \| null | нет | дата архивации, `null` если активна |
| `sort_order` | integer | нет | шаг 10, по умолчанию `(max+10)` |
| `value` | null | нет | резерв под счётчики, в v1.0 всегда `null`, парсер сохраняет |

### 4.3. Entry

```json
{"type":"entry","habit_id":1,"date":"2026-10-30","status":"done",
 "note":"глава 7","value":null,"updated_at":"2026-10-30T22:14:03+02:00"}
```

| Поле | Тип | Обяз. | Правила |
|---|---|---|---|
| `type` | string | да | всегда `"entry"` |
| `habit_id` | integer | да | ссылка на существующую привычку |
| `date` | string(date) | да | реальная календарная дата, не в будущем, не раньше `start_date` привычки |
| `status` | enum | да | `"done"` или `"skipped"` |
| `note` | string | нет | 0..500 символов, по умолчанию `""` |
| `value` | null | нет | резерв, в v1.0 `null` |
| `updated_at` | string(datetime) | да | ставит сервер |

Естественный ключ — `(habit_id, date)`. Отсутствие записи означает «не отмечено»; отдельного статуса «провалено» нет: промах вычисляется как плановый день в прошлом без отметки.

### 4.4. Schedule

```json
{"kind":"daily"}
{"kind":"weekdays","days":[1,3,5]}
{"kind":"weekly_count","times":3}
```

| `kind` | Поля | Правила |
|---|---|---|
| `daily` | — | каждый день |
| `weekdays` | `days` | ISO-дни: 1 = понедельник … 7 = воскресенье; непустое подмножество без повторов |
| `weekly_count` | `times` | целое 1..7, квота на ISO-неделю (пн–вс) |

Неизвестный `kind` делает строку невалидной (см. 4.5).

### 4.5. Валидация

**Входящие данные (API).** Первая ошибка в порядке полей формы возвращает `400` с машиночитаемым кодом:

```json
{"error":{"code":"invalid_name","message":"Название должно быть от 1 до 80 символов","field":"name"}}
```

Коды: `invalid_name`, `invalid_description`, `invalid_color`, `invalid_icon`, `invalid_category`, `invalid_schedule_kind`, `invalid_schedule_days`, `invalid_schedule_times`, `invalid_date`, `date_in_future`, `date_before_start`, `invalid_status`, `invalid_note`, `habit_not_found`, `entry_not_found`.

Дополнительно: входной JSON обязан быть валидным UTF-8; глубина вложенности ≤ 32; тело запроса ≤ 1 МиБ.

**Загрузка файла (политика «спасать данные, не падать»):**

| Ситуация | Поведение |
|---|---|
| Обрезанная последняя строка | Отбросить, предупреждение в stderr, пометить файл к перезаписи |
| Строка не парсится как JSON | То же, что выше |
| Неизвестный `type` | Пропустить в логике, сохранить при перезаписи |
| Неизвестные поля | Сохранить, игнорировать |
| Дубликат `(habit_id, date)` | Побеждает последний, предупреждение |
| `entry` без привычки | Отбросить, предупреждение |
| `id` привычек дублируются | Второй получает новый `id`, предупреждение |
| `schema_version` > поддерживаемой | Отказ старта, данные не изменяются, код выхода 2 |
| Файл больше 64 МиБ | Отказ старта с сообщением (защита от исчерпания памяти) |

После любого восстановления делается резервная копия исходного файла: `data/habits.jsonl.corrupt-YYYYMMDD-HHMMSS`.

### 4.6. Quit (вредная привычка, v1.1)

```json
{"type":"quit","id":1,"name":"Не курю","description":"","color":"#ef4444",
 "icon":"no-smoke","started_at":"2026-10-18T16:57:00+03:00",
 "created_at":"2026-10-30T20:22:00+03:00","best_seconds":1532100,
 "attempts":3,"archived_at":null,"sort_order":10}
```

| Поле | Тип | Правила |
|---|---|---|
| `started_at` | datetime | ISO 8601 с offset; начало текущей попытки, не в будущем |
| `best_seconds` | integer | длительность лучшей завершённой попытки, ≥ 0 |
| `attempts` | integer | число попыток, включая текущую, ≥ 1 |
| `archived_at` | date \| null | как у привычек |

`best_seconds` для отображения считается как `max(best_seconds, now − started_at)`: текущая
попытка участвует в лучшем результате. При сбросе разница `at − started_at` записывается в
`best_seconds`, если она больше, `attempts` увеличивается, `started_at` становится `at`.
Дробные секунды в ISO-времени принимаются и нормализуются к виду без дроби.

### 4.7. Краевые случаи модели

1. **Смена расписания задним числом.** Статистика всегда считается по *текущему* расписанию привычки; отметки не пересчитываются и не удаляются. Исторические версии расписаний не хранятся (см. 12, вопрос Q2).
2. **Удаление привычки.** Основное действие — архив; удаление только с подтверждением и удаляет все `entry` этой привычки. Копия остаётся в `.bak`.
3. **Часовой пояс.** Даты хранятся как гражданские (без зоны). «Сегодня» вычисляется в зоне системы на момент запроса; переезд в другой пояс не ломает историю.
4. **Начало отслеживания.** Привычка с `start_date = 2026-10-30` не имеет промахов за 29 октября.
5. **Привычка в архиве.** Её серия фиксируется на `archived_at` и не растёт; отметки на даты после архивации запрещены.
6. **Привычка без отметок.** Серия равна 0 и не считается «порванной».

## 5. Расписание и статистика

Раздел определяет все вычисления; при расхождении кода и этого раздела прав раздел.

### 5.1. Плановые дни

Функция `is_planned(habit, date)` — истинна, если `date >= habit.start_date` и:

- `daily` — всегда;
- `weekdays` — `iso_weekday(date) ∈ schedule.days`;
- `weekly_count` — всегда истинна (день потенциально плановый, ограничение накладывается квотой недели).

Функция `week_quota(habit, week)` для `weekly_count` — `max(0, times - skipped_count(week))`, где `skipped_count` — число пропусков в этой ISO-неделе. Пропуск уменьшает квоту, а не засчитывается как выполнение.

### 5.2. Список «Сегодня»

Для выбранной даты `D` в список попадают активные привычки, у которых:

- `daily` и `weekdays` — `is_planned(habit, D)` истинна;
- `weekly_count` — всегда; прогресс недели показывается рядом, закрытая квота не скрывает привычку (иначе нельзя снять ошибочную отметку).

Сортировка: `sort_order`, затем `id`.

### 5.3. Серия (streak)

**Единица серии** зависит от расписания: для `daily` и `weekdays` — дни, для `weekly_count` — недели. В интерфейсе подпись меняется соответственно («дней подряд» / «недель подряд»).

**Правила для дневных расписаний.** Идём по датам назад от опорной даты, рассматривая только плановые дни:

- `done` → серия +1, продолжаем;
- `skipped` → серия не меняется (не рвёт, но и не добавляет), продолжаем;
- плановый день в прошлом без отметки → серия останавливается;
- доходим до `start_date` → серия закончилась естественно.

**Опорная дата и «льгота на сегодня»:** если сегодня плановый день и он ещё не отмечен, отсчёт начинается с предыдущего планового дня — незакрытый текущий день не обнуляет серию.

**Правила для `weekly_count`.** Идём по ISO-неделям назад:

- неделя закрыта (`done_count >= week_quota`) → серия +1;
- текущая неделя не закрыта → не рвёт, не добавляет;
- прошедшая неделя не закрыта → серия останавливается.

**Лучшая серия** вычисляется тем же алгоритмом по всей истории привычки (от `start_date` до `min(archived_at, сегодня)`); при объёме данных до 100 тыс. отметок это линейный проход, допустимый на каждый запрос.

Примеры (ежедневная привычка, сегодня 2026-10-30, отметки за 29 и 28 октября — `done`):

| Сценарий | Ожидаемая серия |
|---|---|
| Сегодня не отмечено, 29 и 28 — `done` | 2 |
| Сегодня `done`, 29 — `skipped`, 28 — `done` | 2 |
| 29 — нет записи, 28 — `done`, сегодня не отмечено | 0 |
| Привычка создана сегодня, отметок нет | 0 (не «порвана») |
| Расписание пн/ср/пт, сегодня четверг, ср и пн — `done` | 2 |

Пример для `weekly_count = 3`, текущая неделя: 1 `done`

| Сценарий | Ожидаемая серия |
|---|---|
| Прошлая неделя закрыта (3 `done`), текущая 1 `done` | 1 |
| Прошлая неделя 2 `done` + 1 `skipped` (квота 2, закрыта), текущая пустая | 1 |
| Прошлая неделя 2 `done`, квота 3, текущая пустая | 0 |

### 5.4. Процент выполнения

За период `[from, to]`, обрезанный по `[start_date, сегодня]`:

- **дневные расписания:** `rate = done / max(1, planned − skipped)`, где `planned` — число плановых дней периода, `skipped` — число пропусков среди них. Промахи попадают в знаменатель и снижают процент.
- **`weekly_count`:** период разбивается на ISO-недели; для каждой недели `credit = min(1, done_count / max(1, week_quota))`; `rate` = среднее `credit` по неделям с положительным знаменателем. Текущая незакрытая неделя в расчёт не входит и показывается отдельной строкой «на этой неделе: 2 / 3».

Округление — до целых процентов, `0 / 0` отображается как «—», а не как `0%`.

### 5.5. Heatmap

Сетка: 12 ISO-недель (пн–вс), 7 строк × 12 столбцов, последняя колонка — текущая неделя. Состояния клетки:

| Состояние | Условие | Цвет |
|---|---|---|
| `done` | есть `entry` со статусом `done` | цвет привычки, полная заливка |
| `skipped` | есть `entry` со статусом `skipped` | нейтральный, штриховка |
| `miss` | плановый день в прошлом без отметки | приглушённый красноватый |
| `off` | неплановый день или день до `start_date` | фон |
| `future` | дата позже сегодняшней | фон с пониженной непрозрачностью |

Для `weekly_count` клетки дней окрашиваются по факту отметки, а «промах» не показывается — вместо него под сеткой индикатор закрытия недели.

### 5.6. Границы расчётов

- Сегодняшняя дата и «сейчас» вычисляются один раз на запрос и передаются внутрь вычислений (детерминированность и тестируемость).
- Все функции статистики — чистые: принимают `habit`, массив `entry`, `today`, возвращают значение. Никакого доступа к файлам и времени внутри.
- Тесты фиксируют «сегодня» параметром, поэтому не зависят от реальной даты.

## 6. HTTP API

### 6.1. Общие правила

- База: `http://127.0.0.1:<port>/api/v1`, только JSON, `Content-Type: application/json; charset=utf-8`.
- Методы: `GET`, `POST`, `PATCH`, `PUT`, `DELETE`. Ответы без тела — `204`.
- Тело запроса ≤ 1 МиБ, заголовки ≤ 16 КиБ, таймаут соединения 30 с.
- Сервер однопоточный (цикл `poll`), запросы обрабатываются последовательно; состояние в памяти, запись на диск — синхронно после каждого изменяющего запроса.
- Идентификаторы в путях — целые числа.
- Даты в путях и query — `YYYY-MM-DD`.

### 6.2. Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/health` | `{"status":"ok","version":"1.0.0"}` |
| GET | `/api/v1/habits?archived=false` | список привычек |
| POST | `/api/v1/habits` | создать |
| GET | `/api/v1/habits/{id}` | одна привычка |
| PATCH | `/api/v1/habits/{id}` | частичное обновление |
| DELETE | `/api/v1/habits/{id}` | удалить вместе с отметками |
| POST | `/api/v1/habits/{id}/archive` | в архив (`archived_at` = сегодня) |
| POST | `/api/v1/habits/{id}/unarchive` | из архива |
| GET | `/api/v1/habits/{id}/entries?from=&to=` | отметки за диапазон |
| PUT | `/api/v1/habits/{id}/entries/{date}` | upsert отметки |
| DELETE | `/api/v1/habits/{id}/entries/{date}` | снять отметку |

| GET | `/api/v1/export` | скачать JSONL (`Content-Disposition: attachment`) |

### 6.4. Ошибки

| Код | Когда | Тело |
|---|---|---|
| 400 | невалидные данные | `{"error":{"code","message","field"}}` |
| 404 | нет привычки/отметки | `{"error":{"code":"habit_not_found"}}` |
| 405 | метод не поддержан | `{"error":{"code":"method_not_allowed"}}` |
| 409 | второй экземпляр, конфликт архивации | `{"error":{"code":"conflict"}}` |
| 413 | тело больше лимита | `{"error":{"code":"payload_too_large"}}` |
| 500 | внутренняя ошибка, в т.ч. сбой записи файла | `{"error":{"code":"internal"}}` |

При ошибке записи на диск изменяющий запрос возвращает `500` и **откатывает** изменение в памяти (состояние в памяти и в файле не расходятся).

### 6.5. Безопасность и локальность

- Сокет слушает только `127.0.0.1`; внешние интерфейсы не используются.
- Проверка заголовка `Host`: допустимы `127.0.0.1:<port>` и `localhost:<port>`, иначе `403` (защита от DNS rebinding).
- Для изменяющих методов (`POST`/`PATCH`/`PUT`/`DELETE`) заголовок `Origin` обязан отсутствовать или указывать на тот же origin; дополнительно требуется `X-Requested-With: habits` — это отсекает межсайтовые POST из браузера.
- Авторизации нет by design; при этом сервер не принимает соединения извне и не читает произвольные файлы (никаких параметров-путей).
- Логи не содержат названий привычек и заметок на уровне `info` (только `debug`).

## 7. Интерфейс

### 7.1. Экраны

| Экран | Содержимое |
|---|---|
| «Сегодня» | Заголовок с датой и стрелками, список привычек: иконка, название, серия, прогресс недели, большая кнопка отметки, меню «пропуск / заметка / редактировать» |
| «Привычки» | Список всех активных привычек с расписанием, кнопка «Добавить», архив (свёрнутый блок) |
| «Статистика» | Выбор привычки и периода, карточки «серия / лучшая / процент», heatmap 12 недель, таблица по неделям |
| «Бросаю» | Карточки вредных привычек с живым таймером (дни и `ЧЧ:ММ:СС`), лучшим результатом и числом попыток; кнопки «сорвался», архив, редактирование |
| «Настройки» | Язык (en/ru/uk), тема (светлая/тёмная/системная), путь к данным (только чтение), экспорт, версия |

Навигация — боковая панель на широких экранах, нижняя вкладка на узких (< 720 px).

### 7.2. Взаимодействие

- Отметка «выполнено» — клик по строке или `Space`; повторный клик снимает отметку.
- «Пропущено» — через контекстное меню строки (три точки) или `S`.
- Заметка — всплывающее поле под строкой, сохранение по `Enter`, отмена по `Escape`.
- Оптимистичное обновление: UI меняет состояние сразу, при ошибке возвращает прежнее и показывает тост.
- Все изменяющие запросы отправляются с `X-Requested-With: habits`.
- Блокировка кнопок во время запроса запрещена (кроме формы создания) — интерфейс должен оставаться отзывчивым.

### 7.3. Локализация

- Файлы `web/i18n/{en,ru,uk}.js`, плоские ключи вида `today.title`, `stats.streak_days`, одинаковый набор во всех трёх.
- Выбор языка: `localStorage["lang"]` → `navigator.language` (`uk-*` → `uk`, `ru-*` → `ru`, иначе `en`).
- Код языка — `uk` (ISO 639-1), в переключателе подпись «Українська»; тег `ua` не используется.
- Даты и числа — через `Intl.DateTimeFormat` / `Intl.NumberFormat` с текущей локалью.
- Множественные формы: `plural(n, {one, few, many})` для ru/uk и `{one, other}` для en; формы задаются в словаре языка, не в коде.
- Тест сборки проверяет совпадение наборов ключей и отсутствие «сирот» в шаблонах.
- Пользовательские данные (названия, заметки) не переводятся и не нормализуются.

### 7.4. Оформление

- Тема: CSS-переменные, `prefers-color-scheme` по умолчанию, ручное переключение в настройках.
- Цвет привычки используется для акцентной полосы, кнопки и клеток heatmap.
- Доступность: фокус видим, контраст ≥ 4.5:1 для текста, все действия доступны с клавиатуры, у кнопок-иконок есть `aria-label`.
- Никаких внешних CDN, шрифтов и иконок — только локальные файлы (офлайн-работа и отсутствие зависимостей).

## 9. Архитектура и сборка

### 9.1. Слои

```
main.c → http (транспорт) → api (маршрутизация, валидация, JSON) → core (модель, расписание, статистика)
```

### 9.3. Сборка

- `make` → `build/habits`; `make test` → сборка и прогон тестов; `make asan` → тесты с `-fsanitize=address,undefined` (нужен установленный `libasan`; в минимальных контейнерах его может не быть — тогда цель недоступна, обычные тесты работают); `make fmt` → `clang-format -i`.
- Флаги: `-std=c11 -Wall -Wextra -Wpedantic -Werror -D_POSIX_C_SOURCE=200809L -O2` (в debug — `-O0 -g`).
- Генерация `web_bundle.c` — шагом сборки (`xxd -i`-подобный скрипт на `sh` + `od`, без Python-зависимости).

### 9.4. Стиль кода

- `snake_case` для функций и переменных, `PascalCase` — только для типов, суффикс `_t`.
- Никаких глобальных изменяемых переменных, кроме состояния сервера, переданного явным указателем.
- Публичные функции — с комментарием над объявлением (что, инварианты, владение памятью).
- Память: единый стиль владения — функция, выделившая объект, описана в комментарии; парсер JSON возвращает дерево, владелец — вызывающий.

## 10. Тестирование

### 10.1. Unit-тесты (ядро)

- `schedule`: плановые дни для всех трёх видов, границы недель, ISO-дни, високосные годы, `start_date`.
- `stats`: все строки таблиц из 5.3 и 5.4 как отдельные кейсы, включая границы «сегодня не отмечено» и пустую историю.
- `json`: экранирование, `\uXXXX`, суррогатные пары, вложенность, обрезанный вход, невалидный UTF-8.
- `store`: сохранение/загрузка, дубликаты, битая последняя строка, откат при ошибке записи (через каталог только для чтения), восстановление `.bak`.
- `quit`: разбор ISO-времени с дробными секундами, сохранение/загрузка счётчика, сброс с сохранением лучшего результата, архив.

### 10.2. Интеграционные тесты

- Обработчики API вызываются напрямую с синтетическими `HttpRequest`: CRUD, отметки, ошибки 400/403/404, экспорт, статика.
- Проверка, что после каждого `PUT` файл на диске содержит изменение (перечитываем файл).
- Проверка защиты: `Host: evil.com` → 403, отсутствие `X-Requested-With` у `POST` → 403.
- Проверка второго экземпляра на том же `--data` — вручную (сокет-сервер блокирующий, поэтому тесты не поднимают его).

### 10.3. CI

GitHub Actions: матрица `gcc`/`clang`, `make test`, `make asan`, проверка `clang-format --dry-run --Werror`, сверка ключей i18n.

### 10.4. Критерии приёмки v1.0

1. Чистая машина с gcc: `git clone && make && ./build/habits` — приложение работает без установки пакетов.
2. Все unit- и интеграционные тесты зелёные, ASan/UBSan чисты.
3. Данные переживают `kill -9` в момент записи: при следующем старте состояние корректно.
4. Три языка переключаются без перезагрузки, ключи не разъезжаются.
5. Отметка на сегодня и на прошлый день, снятие отметки, пропуск с заметкой работают с клавиатуры.
6. Серии и проценты совпадают с примерами раздела 5.
7. Второй экземпляр не запускается и не портит файл.

## 13. Риски

| Риск | Влияние | Смягчение |
|---|---|---|
| Портативные данные рядом с бинарником не пишутся (read-only, установка в `/usr/bin`) | приложение не стартует | явная ошибка с подсказкой `--data`, документация «распакуй в свою папку» |
| Самописный HTTP/JSON содержит ошибки разбора | падения, порча данных | fuzz-тесты парсера на этапе M1, лимиты размеров, отказ вместо «угадывания» |
| Смена расписания искажает старую статистику | недоверие к цифрам | зафиксированное правило 4.7.1 и предупреждение в UI при смене расписания |
| Рост файла при годах истории | замедление старта | лимит 64 МиБ с внятной ошибкой, линейный парсер; при необходимости — переход на журнал и компакцию |
| Расхождение i18n-ключей | «сырые» ключи в UI | тест на равенство наборов ключей в CI |
| Пользователь запускает второй экземпляр и теряет данные | потеря отметок | `flock` + отказ с кодом 1 |

## 14. Вне рамок

Явно не делаем (ни в v1.0, ни в ближайших планах):

- напоминания, push- и любые уведомления;
- счётчики, таймеры, частичное выполнение, подзадачи;
- несколько пользователей, аккаунты, авторизация, TLS;
- синхронизация между устройствами, облако, мобильное приложение;
- PWA и service worker;
- теги (кроме одной категории), зависимости между привычками;
- графики кроме heatmap (линейные, столбчатые, «прогнозы»);
- импорт данных и миграция из других трекеров;
- Windows и macOS (код по возможности переносим, но поддержка не заявляется).
